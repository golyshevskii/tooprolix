## Reproduce

```bash
uv run python3 corpus/measure.py --lock corpus/corpus.lock                   # the distributions
uv run python3 corpus/measure.py --lock corpus/corpus.lock --inspect <repo>  # one repo in detail
make test                                                                    # 57 guards
```

`uv run python3`, not bare `python`: a harness hook blocks the bare interpreter. The task file's
`python corpus/measure.py ...` is intent, not a runnable command.

**Interpreter: CPython 3.14.6, Darwin 25.5.0, arm64.** This matters and is enforced.
Determinism holds on a fixed interpreter, *not* across versions: PEP 701 (Python 3.12) made
f-string interpolations emit `NAME` tokens, so pre-3.12 `tokenize` cannot see identifiers inside
an f-string, so the restatement probe undercounts. The mechanism is independently checkable and
is the part worth trusting:

```bash
uv run --python 3.11 --no-project python3 -c "import tokenize,io; print([t.string for t in tokenize.generate_tokens(io.StringIO('x = f\"count {counter} done\"\n').readline) if t.type==tokenize.NAME])"
# 3.11 -> ['x']          3.12 and 3.14 -> ['x', 'counter']
```

The size of the effect was 133 candidates instead of 137 on the audited repository, same commit,
identical block counts. **That pair of counts is NOT reproducible with the shipped script**: it
was measured during development, before the guard existed, and `measure.py` now exits 2 below
3.12. It is quoted only to show the magnitude (~3%) behind the floor, and no constant depends on
it. `measure.py` refuses to run below 3.12 (`MIN_INTERPRETER`) and `requires-python` is `>=3.12`
to match. Everything else — prose share, block sizes,
duplicate counts — is identical across 3.11 and 3.14.

First run clones the pinned corpus into `corpus/checkouts/` (git-ignored, disposable). The user's
own working copies are never touched: they are used read-only as clone *sources*. A checkout is
accepted only if HEAD equals the pin **and** the worktree is clean with no untracked `.py` — the
SHA alone does not pin the bytes that get measured.

### What is counted

| Term | Definition |
|---|---|
| prose block | a docstring (module, class, function, async function), or a maximal run of adjacent **own-line** `#` comments glued into one block |
| trailing comment | a `#` comment sharing a line with code — counted separately, **never** a block |
| block size | physical lines (`end_lineno - lineno + 1`), the unit the issue measured 7/55 in; also normalised **words** |
| prose share | `prose_lines / total_lines` — see the cross-check below |
| normalisation | lowercase, every non-alphanumeric character to a space, whitespace collapsed |
| line buckets | every physical line is prose **or** blank **or** code, exactly once; prose wins (a blank line inside a docstring is docstring) |

Not counted, deliberately: bare string expressions used as pseudo-docstrings, README/docs prose
(Python only in this pass), and non-`.py` files.

### Exclusions (denominator hygiene)

A ratio computed over a virtualenv, a build tree or generated code is wrong, and every constant
derived from it is wrong with it. The full exclusion list is **printed by the script itself** —
see the `excluded ...` and `generated-header markers` lines at the top of section 6, emitted from
the same constants the walk uses, so the list in this document cannot drift from the list that
was applied. It covers virtualenvs, caches, build/dist trees, `node_modules`, `site-packages`,
vendored and third-party trees, migrations, protobuf stubs, `.pyi` stubs, `*.egg-info`, and any
file whose first 6 lines carry a machine-generated header.

Path components are compared **case-folded and after resolving symlinks**, and each real file is
counted once however many links reach it. Generated-header markers are **anchored** — they count
inside a `#` comment or at the start of a line's text, never as a bare substring, so a docstring
saying "IDs are generated by the server" no longer excludes a hand-written file.

Files the stdlib parser rejects are **counted and reported in the main table** (`skip_bad`), never
silently dropped — crewAI's 5 are Jinja templates named `.py`. Files with a machine header are
reported the same way (`skip_gen`, pydantic 1). Both columns sit beside the numbers they are
missing from.

# The four decisions

## 1. Detector priority — **duplicates (detector 1) first**

**What this decision does NOT rest on: a precision comparison.** Labelling is task 7's job — its
AC1 requires >= 20 labelled findings in `corpus/annotations.md` at precision >= 0.8, and the
audited repository yields only 8 candidates, so that floor cannot be reached here at all. My own reading
of those 8 gives a precision **range of 0.63 to 1.00 at n=8** (8/8 are copies I would delete;
5/8 if a reviewer rates the three parallel `publish_create/delete/edit` docstrings as acceptable
parallel structure). The bottom of that range does **not** clear 0.8, the sample is a quarter of
the required size, and it is my unblinded judgement rather than a protocol. **The precision
question is open and task 7 settles it.**

What the decision rests on instead, from section 6.4 and the `--inspect` listing:

| | detector 1 (duplicates) | detector 2 (restatement) |
|---|---|---|
| candidates on the audited repository | **8** | **137** (132.4 per 1000 comment blocks) |
| corpus-wide candidates | 1470 | 3158 |

1. **The issue's mandate, which is external evidence.** Its manual pass found the win came from
   deleting copies, not from compressing prose. That is the one labelled result anybody has, and
   it points at detector 1.
2. **Volume on an already-audited repo.** the audited repository's prose was reviewed by a human and
   an opus pass; detector 2 still proposes **137** changes to it against detector 1's **8**. The
   human's decision to *keep* those 137 comments is evidence about them that needs no labelling
   from me: whatever detector 2 is finding, the audit already considered and declined it 137
   times. Shipping that first means shipping 137 arguments with the author of the cleanest repo
   in the corpus.
3. **Detector 2 owns a false-positive class that detector 1 does not.** Commented-out code is
   `ruff ERA001`'s job and the issue puts it Out of scope, so any hit in that class is a false
   positive by construction. Computed, not eyeballed (`commented` column): **420 of pydantic's
   514** candidates (81.7%) parse as Python, and **20 of the audited repository's 137** (14.6%);
   corpus-wide **453 of 3158** (14.3%). Honest caveat: this is overwhelmingly a pydantic
   phenomenon. Excluding pydantic and that repository, the other five repos run **0.0% to 1.3%**
   (requests 0/21, OpenHands 2/1255, agents 4/597, langgraph 5/485, crewAI 2/149), so it is a
   real class where it bites and near-absent elsewhere — not a uniform tax on detector 2.

Detector 2's remaining failure mode is qualitative and I record it as an observation, not a
measurement: comments that carry a fact the code does not — a comment naming the numeric id behind
a symbolic constant, where the identifier repeats the name and the comment holds the number.
Deleting those loses the "why", which the issue calls unrecoverable.
How often it happens is not established here.

**Counter-evidence, stated rather than buried:** raw frequency favours detector 2 — 3158
candidates against 1470 duplicate pairs, and it leads in most repositories. Frequency is not the
criterion, because the issue's AC1 is a precision AC; but on frequency alone detector 2 would
win, and that is worth knowing.

## 2. Similarity threshold — **Jaccard over 3-word shingles >= 0.75. Issue hypothesis CONFIRMED, not moved.**

Two separate questions, two separate numbers.

**Which metric** — section 6.5 "Metric agreement", both metrics scored on the *same* pairs at the
same 0.75 cutoff. `jaccard_only` runs **0 to 2** (0 in most repositories); `difflib_only` runs
**73 to 150**. So Jaccard >= 0.75 is very nearly a subset of difflib >= 0.75: difflib admits far
more pairs at the same nominal number and finds almost nothing Jaccard misses. For a detector
whose binding constraint is precision, take the conservative metric. (This is also why the rough
`difflib` pass the task asked for stayed a *comparison* and did not become the metric.)

The sample behind that table is 2000 pairs drawn at **evenly spaced indices spanning the whole
sorted pair list**, both ends included — not the first 2000, which would have scored every pair
in `a_*.py` and none in `z_*.py`. Exact duplicates are excluded from it, since they are trivially
1.0 under both metrics and would only dilute the comparison. `sampled` in the table is the actual
count.

**Which value** — the decision table, the audited repository at the chosen `2ln/8w` cutoff:

| >=0.5 | >=0.6 | **>=0.75** | >=0.9 | >=1.0 |
|---|---|---|---|---|
| 28 | 22 | **8** | 8 | 4 |

The knee sits between 0.6 and 0.75: 22 -> 8, a 2.75x drop. Relaxing to 0.6 admits **14 further
unlabelled candidates** on a repo whose prose a human and an opus pass already audited — whether
those 14 are false positives is *not established here*, but tripling the candidate count on the
cleanest repo in the corpus is the cost, and nothing in the measurement offsets it. Tightening to
0.9 changes **nothing** on that repository (8 = 8) while reducing candidates elsewhere at `2ln/8w`:
the corpus-wide pool falls from **1470 to 1167, which is -20.6%** — not "about half". All seven
repos, because the relative losses differ by a factor of five and quoting only the extremes
misleads: OpenHands 90 -> 49 (-46%), crewAI 196 -> 110 (-44%), the audited repository 8 -> 8
(0%), langgraph 682 -> 582 (-15%), openai-agents-python 134 -> 118 (-12%), pydantic 343 -> 296
(-14%), requests 17 -> 4 (-76%). langgraph alone is 682 of the 1470, so the aggregate tracks its
-15% far more than it tracks requests' -76%. Whether the candidates 0.9 gives up are true
positives is unlabelled either way; what is *measured* is that 0.75 costs nothing on the
audited repository and buys a fifth more candidates corpus-wide. 0.75 also has to be
<= 0.932 to reach the three-member cluster in that repository.

## 3. Minimum prose-block size — **>= 2 physical lines AND >= 8 normalised words**

A conjunction, because each dimension alone provably fails. This is the constant task 3 needs.

**Lines alone are not enough.** `Init API instance.` written as a docstring across three physical
lines is 3 words, and it produced a real J=1.000 false pair between
two sibling API-client modules — through any line cutoff <= 3.
That is precisely the `Initialize the class.` class this decision exists to kill.

**Words alone are not enough.** A min-word cutoff of 8 with no line requirement leaves **360**
pairs on the audited repository, because one-line comments carrying long copy-pasted strings clear
it — the `# MySQL palette: https://coolors.co/...` comment appears 17 times.

**One-line blocks are where the noise lives** (section 6.4, exact pairs by size):

| repo | 1-line exact pairs | all exact pairs | share |
|---|---|---|---|
| OpenHands | 741861 | 741970 | **99.99%** |
| pydantic | 32795 | 33090 | 99.11% |
| the audited repository | 422 | 427 | 98.83% |

Those are pytest scaffolding (`# Arrange` x801, `# Act` x630, `# Assert` x622) and codegen markers
(`# insert assert exc_info.value.errors(include_url=False)` x239 in pydantic). Without a cutoff
the audited repository yields **451** candidates at 0.75, and OpenHands **742095** — a detector nobody
would keep switched on.

**Where 8 words comes from, stated as the range it is.** On the audited repository at 0.75 the
candidate count is flat across a plateau and only then declines:

| cutoff | 2ln/6w | **2ln/8w** | 2ln/10w | 2ln/12w | 2ln/16w |
|---|---|---|---|---|---|
| candidates | 8 | **8** | 8 | 7 | 6 |

Identical counts on a nested family mean identical *sets*, so **any cutoff from 6 to 10 words
yields exactly the same 8 findings**; 12 words drops one (an 11-word duplicated
block) and 16 drops two. So **10 words, not 8, is the largest cutoff that keeps every finding on
this repo** — 8 is the **conservative end of a measured 6-10 word plateau**, and I am not moving
the constant to 10 because the plateau means that repository cannot distinguish them (n=8, one repo),
while across the corpus the difference is a rounding error (at 0.75: OpenHands 90 vs 88, crewAI
196 vs 195, langgraph 682 vs 678, pydantic 343 vs 342, requests 17 vs 17). Task 7 has the labelled
sample to settle 8 against 10; on the evidence here they are the same decision.

The line half is separately justified: `3ln/12w` gives 6 on that repository because 3 lines discards
a genuine 2-line/20-word cross-file copy (J=1.000). Acknowledged cost of the word half: it silences
841 of 2033 blocks (<8w) on the audited repository. That is the intent — that is the boilerplate mass
— and section 6.3 gives the `<Nw` column per repo so task 3 can see the price.

## 4. Detector 3 (volume budget) — **stays OFF. No enabling task.**

> 🔄 **REVERSED 2026-07-26 by the owner — see EPIC.md Decisions #1.** The measurement below is
> not overturned; its *precondition* changed. Volume ships as `TPX001`/`TPX002` with an opt-out
> marker, so the question stopped being "does it flag" and became "how many markers does it
> cost" — **10** on the audited repository at the shipped 200/150. That block therefore **does** flag and is silenced by one marker; §7 and
> `corpus/annotations.md` §3 carry the measurement. Kept unedited below as the record of what
> was true when written.

The issue predicted an AC3-vs-AC5 conflict; section 6.3 measures it.

On the audited repository the largest prose block is **55 lines** — one block,
the gate truth table, the one block the issue names as must-never-flag — and blocks **over 55
lines: 0**. So every global line threshold is one of two useless things: <= 55 flags the truth
table, > 55 fires zero times there. There is no third option on the repo the detector was supposed
to help.

A `> 55` threshold is not harmless elsewhere either: **langgraph 45** blocks and **pydantic 18**
exceed it, and the biggest are exactly the documentation worth having —
`langgraph/pregel/main.py:454` (250 lines), `pydantic/fields.py:1729` (145). A budget rule would
fire hardest on the best-documented API surfaces in the corpus.

Nor is one global number defensible: p99 block size ranges **13 to 37 lines** across the seven
repos, a 2.8x spread. Any workable threshold is per-repo calibration — a config feature, not a
detector.

Verdict: stays off for 0.1.0, and these numbers do **not** justify opening an enabling task yet.
Two prerequisites, in order, if it is ever revisited: (a) the opt-out marker must exist and the
canonical places must be marked, per the issue; (b) the unit should be **words, not lines** —
w_p90 spans 25-49 against line p90 6-19, so words separate the population better.

What was fixed:

1. **The duplicate machinery had no test at all.** Stubbing `duplicate_stats()` to
   `return DuplicateStats()` left the old suite green while every threshold table went to zero;
   so did disabling the prose exemption in the classifier. Now guarded by `tests/unit/test_duplicates.py`
   (exact grouping, candidate generation, Jaccard on a hand-computed pair, the conjunction cutoff
   on **both** the exact and the near-duplicate paths, the cap regression, sample uniformity).
   The near-duplicate half of that was missing until item 8 — see there for what was and was not
   actually guarded.
2. **The DF cap deleted exactly what a duplicate detector is for.** 41 identical blocks put every
   shingle they own in an over-cap bucket, so the tables read 0 while exact grouping read 820.
   Exact groups now reach the tables arithmetically (all their pairs are J=1.0 by definition, so
   no comparison is needed), and the cap's residual cost is printed as `capped_sh` / `capped_bl`
   beside every table it affects. `cand_pr` is now index pairs **plus** exact pairs.
3. **Compare-before-normalise in the exclusion filter.** `pkg.egg-info/generated.py`, `Vendor/`
   and a symlink into `vendor/` all bypassed it. Paths are now resolved and case-folded before
   comparison, `.egg-info` is matched as a path component, and one real file reached by two links
   counts once.
4. **The commented-out-code classifier was wrong in both directions**, and it sets the pivotal
   figure behind decision 1. `# source / destination` (a `BinOp`) was scored as code; a bare
   attribute access like `# config.retry_limit` was exempted as prose. Both fixed and tested.
5. **Generated-file detection was a bare substring match** — a docstring saying "IDs are generated
   by the server" excluded the whole file from every denominator. Markers are now anchored.
6. **Checkout integrity was asserted from `HEAD == sha` alone**, so editing a file in
   `corpus/checkouts/` changed stdout while the pin still "matched". A clean worktree with no
   untracked `.py` is now required, and a dirty one fails loud.
7. **`requires-python` said 3.11 while the script refuses to run below 3.12.** Latent only because
   uv happened to select 3.14; now `>=3.12`, so ruff's `target-version` and ty's `python-version`
   are no longer inferred from a version the script rejects.
8. **The near-duplicate conjunction loop was never guarded, and this document claimed it was.**
   Found by a third review after the fixes above. Changing `and` to `or` in the near-duplicate
   size test left all 57 tests green: every conjunction test built *identical* blocks, which form
   an exact group and are counted through the separate arithmetic path, so the near-duplicate loop
   contributed to no assertion. That loop is not a corner case — **4 of the audited repository's 8
   findings (the J=0.932 and J=0.941 pairs) and the whole 28/22/8 knee row go through it**, so the
   expression carrying decision 3 was unverified while item 1 above asserted it was covered. Now
   guarded by five tests built from near-identical, non-exact blocks (J=7/9=0.778, plus a
   short-block pair whose texts differ but whose shingle sets are equal, since a 5-word block
   cannot otherwise score above 0.75). Each asserts `exact_groups == 0`, which is what proves the
   pair travelled the near-duplicate path. Mutation-proved three ways: `and` -> `or` (2 red),
   stubbing the loop body (4 red), dropping the threshold check (1 red).

   Nothing about this was RED-before-GREEN, and calling it TDD would be false: the code was
   already correct and the defect was **in the test suite**, not in the behaviour. There was no
   failing-for-the-right-reason state to observe — the honest equivalent is the mutation proof,
   which is what is recorded. Recording it that way, and correcting item 1's overclaim above,
   matters more than the fix: a guarantee this document asserts but no test enforces is worse than
   an admitted gap, because five downstream tasks read these constants on the strength of it.

## 7.1 🔴 The `.gitignore` trap, and the cause this epic had wrong

**Recorded until 2026-07-26, in the task file and in `STATE.md`: the cause is
`tooprolix/.gitignore:33` (`corpus/checkouts/`). That is false**, and the remedy it implied — "run
from a directory with no ancestor `.gitignore` naming `corpus/checkouts/`" — is insufficient,
because the rule is anchored at the path being checked and not at the working directory.

The cause is **a `.gitignore` in an ancestor directory**: a stock Python-template `.gitignore`
sitting in a directory that is **not a git repository at all**, listing `lib/` and `lib64/`. The
CLI builds its walk with `require_git(false)` (`src/cli.rs:496`), so the `ignore` crate collects
`.gitignore` files from the **ancestors** of the start path regardless of repository boundaries,
and `crewAI/lib/**` disappears.

Proved with one file rather than argued — the same bytes, `<dir>/lib/big.py`, a 326-word docstring:

| `<dir>` | result |
|---|---|
| a directory with no ancestor `.gitignore` | `lib/big.py:2: TPX002 docstring is 326 words long…`, **exit 1** |
| a directory under one listing `lib/` | `warning: no Python files under …`, **exit 0** |

**Consequence, and it is not optional: the checkouts must live where no ancestor directory
carries a `.gitignore`.** `corpus/run_all.sh` and `corpus/determinism_check.sh` therefore take `CORPUS_ROOT`
rather than assuming `corpus/checkouts/`.

## 7.3 pydantic 120 vs 121 — the discrepancy, closed

Task 4a recorded **121** `TPX003` clusters for pydantic; the CLI reports **120**, inside the tree
and outside it alike, so the `.gitignore` trap does not explain it.

**Cause: the hidden-entry skip, not `.gitignore`.** The one file the two walks differ on is
`pydantic/.github/actions/people/people.py` — under a `.`-directory, therefore skipped by the CLI,
therefore absent from the 404 — and `git check-ignore` reports nothing for it, so the "the CLI
honours pydantic's own `.gitignore`" hypothesis is **disproved**. That file carries exactly one
self-contained cluster, `people.py:452 ~ people.py:498` at similarity 0.871.

Proof: a copy of pydantic with `.github` renamed to `zgithub` gives `TPX003` **121**, `TPX002` 46,
`TPX001` 1 — one cluster more and nothing else moved.

## 7.5 Determinism and offline behaviour (issue AC2)

`CORPUS_ROOT=<outside> ./corpus/determinism_check.sh`:

* **five** runs on pydantic — 167 findings across all three codes, a deliberately non-empty subject
  — byte-identical in both formats (`text` 41 480 bytes, `json` 179 146 bytes), stdout and stderr;
* the same run under `sandbox-exec -p '(version 1)(allow default)(deny network*)'` is byte-identical
  to the networked run. The sandbox is proved to deny before the result is believed: `curl` must
  fail inside it and succeed outside it, or the check reports failure rather than a pass;
* none of 36 network/ML crate patterns matches any of the **113** crates in `Cargo.lock`; the
  matcher is proved able to fire against a synthetic lock file carrying `reqwest`.

Five passes rather than two, and the number came from a mutation: replacing the output sort with a
per-process coin flip left a two-pass comparison green half the time.

**Known limit, recorded rather than hidden.** Deleting the sort in `cli::findings` does **not**
redden this script: the walk order is itself deterministic on one machine, so the sort's job is
stability across *layouts and machines*, which a same-machine repeat cannot observe. That mutation
reddens exactly one Rust test — `cli::tests::the_findings_are_ordered_whatever_order_the_blocks_arrive_in`
— which is where the guard belongs.

## 7.6 Benchmark (issue AC3): `< 5s`, warm cache

Machine: **Apple M1 Max, 10 cores (8 performance + 2 efficiency), 32 GiB RAM, macOS 26.5.2
(build 25F84)**. Release binary, page cache warmed by a discarded first run, median of 10.

```bash
CORPUS_ROOT=<outside> uv run python3 corpus/bench.py
```

⚠️ **The harness checks its subject and every run before timing anything, and both halves are there
because review defeated the version without them.** Three defects, three guards:

1. The original was a heredoc here using `subprocess.run(..., check=False)`, discarding the exit code
   and the output. Pointed at an **always-failing binary** it reported a green **5.356 ms
   "benchmark"**. `time_run` now aborts on an unexpected exit code or an empty findings list.
2. The first fix raised from `time_run` but review changed `main`'s `return 1` to `continue`: all
   five `time_run` tests stayed green and the benchmark **exited 0** on that same failing binary —
   the identical defect one stack frame up. `TestTheBenchmarkStopsWhenARunFails` runs the real entry
   point and asserts a non-zero return with no timing row, and reddens under exactly that mutation.
3. Neither of those checked *what was being measured*. A substituted `CORPUS_ROOT` holding one
   long-docstring `x.py` per root gives every root exit 1 with non-empty output → benchmark exit 0,
   medians around 15 ms. `verify_subject` now compares the findings against `corpus/runs/<name>.json`
   before timing, so the pinned SHA, the clean worktree and the walked-file count are inherited from
   `corpus/run_all.sh` — one owner for those expectations, not a second copy.

| repo | lines | median | min | max |
|---|---|---|---|---|
| requests | 12 032 | **28.5ms** | 28.3ms | 31.4ms |
| pydantic | 170 389 | **266.0ms** | 263.1ms | 272.0ms |
| langgraph | 185 740 | **287.6ms** | 284.8ms | 290.8ms |
| crewAI/lib/crewai | 211 664 | **339.2ms** | 331.1ms | 346.0ms |
| OpenHands | 240 504 | **448.0ms** | 440.8ms | 452.7ms |
| openai-agents-python | 303 693 | **292.4ms** | 280.9ms | 316.9ms |

⚠️ **These are wall-clock timings on one machine: re-runnable, not byte-reproducible.** The raw
samples are not committed and no assertion depends on them. Three consecutive runs of the committed
harness moved each median by up to ~15%, and an independent reviewer on the same corpus
reproduced every row within that spread — noise far below the quantity being claimed, which is a 5 s budget. The reproducible artifact is the harness
and its guards, not the digits.

No pinned repository is exactly 100 000 lines, so the budget is bracketed rather than hit: 71 746
lines and 170 389 lines sit either side of it, both a few hundred milliseconds. Interpolating,
~100 k lines is **under 250 ms — a margin of more than 20x on the 5 s budget** — and the largest
repository in the corpus, at three times the AC's size, finishes in about a third of a second.

The near-path quadratic risk recorded against this AC did not materialise on real prose: the corpus
has no license-header-style population. It remains real for synthetic input — 2 000 files sharing a
one-token-different header measured 3.05 s — and the lever there is candidate generation, not the
0.75 threshold and not the block size, both of which are measured.

## 7.7 Which unit of volume is more precise (issue AC1b)

Full protocol, blindness mechanism and the 51 annotations are in `corpus/annotations.md` §2.
Calibrated to an equal alert volume (8 comment + 165 docstring alerts, with one cell at 164 where
ties make 165 unreachable — printed, not smoothed), on the 51-block union of symmetric differences
against words:

| unit | precision on the disagreement set |
|---|---|
| `tokens_norm` (cl100k) | **0.269** (7 of 26) |
| **words** (shipped) | **0.231** (6 of 26) |
| `chars_norm` | 0.231 (6 of 26) |
| `tokens_raw` (cl100k) | 0.080 (2 of 25) |

**`tokens_norm` finishes one block ahead of words, and that is reported as it fell.** A margin of a
single true positive out of 26 proposals is not something this sample can resolve. What it does
separate cleanly is the normalised units from the raw one: `tokens_raw` scores about a third of
either, in the predicted direction — raw text is dragged upward by embedded code, JSON and argument
tables, where length is set by the symbol rather than by the author.

Words and `tokens_norm` landing within one block of each other is what the ratio measurement
predicted: on normalised text cl100k charges about one token per word, so they are very nearly the
same unit measured twice. What separates them is portability rather than precision — cl100k charges
**2.14 tokens per word on Cyrillic against 1.01 on English**, so a token threshold fires roughly
twice as early on a non-English codebase while a word threshold does not. **No unit is changed by
this task**: it is frozen in the shipped JSON schema and in user-written `pyproject.toml` limits, so
moving it is an owner decision and second-epic work.

⚠️ 0.231 is not the rule's precision: the disagreement set is by construction the 51 hardest blocks
of 11 574, sitting exactly at the calibrated boundary. It ranks units; it is not a floor.

## 7.8 The anti-false-positive gate (issue AC4/AC5) is not closed here

The gate needs a repository whose prose a human has already cleaned by hand — only there can a
finding be told apart from a false positive. The pinned corpus contains no such repository, so
there is nothing here to measure the gate against, and it moves to the second epic together with
the work of finding or building one. `corpus/annotations.md` §3 states what is deliberately not
offered as a substitute.

AC1, AC1b, AC2 and AC3 are unaffected: each is defined over the pinned corpus as a whole.
